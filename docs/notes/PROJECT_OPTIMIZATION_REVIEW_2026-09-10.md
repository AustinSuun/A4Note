## 三、优先级与验收标准

### P0-A：先修复笔记软删除的读回语义

**证据**：`src-tauri/src/library_notes.rs` 中删除操作设置 `deleted_at`，但 `list_notes_for_paper` 的查询只有 `WHERE paper_id = ?1`，没有排除软删除记录；返回 DTO 也没有把墓碑状态交给界面处理。

本轮把当前列表 SQL 放入隔离内存 SQLite 复现：插入 1 条笔记 → 标记软删除 → 同一列表查询仍返回 1 条。此处证明的是查询层语义不一致，未在真实用户资料库或桌面删除入口上实验。

**建议任务**：区分“正常业务读取”和“同步墓碑读取”；正常阅读/搜索/导出排除删除记录，同步流程仍保留墓碑。不要为了隐藏记录直接物理删行。

**验收**：删除后立即刷新、重开应用均不回显；搜索和导出不包含已删内容；同步 outbox、版本号和墓碑保留；恢复/撤销如属于产品功能，另行明确定义，不靠读取遗漏实现。

### P0-B：备份与恢复先做到失败可回退

**证据**：`src-tauri/src/backup.rs` 直接 `fs::copy` 数据库后递归复制 PDF；恢复时先替换数据库、删除现有文件目录，再复制备份文件。已有安全备份是有价值的，但并不能保证在线数据库和附件一致快照，也没有覆盖复制中断后的自动恢复。

**建议任务**：采用 SQLite 一致性备份机制，并协调附件写入；恢复先在 staging 目录复制、验证可读性/数据库完整性/文件清单，再受控替换，失败保持旧库可用。不要仅把 journal_mode 切为 WAL——当前直接复制单个 DB 文件的假设也必须一起调整。

**验收**：并发保存/导入时备份一致；磁盘不足、损坏备份、附件缺失、复制失败均不破坏当前库；恢复中断有明确回退路径；覆盖工作台、笔记标注及附件，而不只是文献条目数量。

### P0-C：单独安排依赖安全升级

**证据**：本轮审计原始结果保存在 `.build/release-sept10-audit.json`。PDF.js 告警涉及恶意 PDF；读取外来 PDF 是产品核心路径，应优先检查该调用链和修复版本。其余包需区分编辑器运行时与构建工具链的实际可达性。

**建议任务**：按 PDF.js → 编辑器相关依赖 → 构建链逐组修复，核对 advisories、lockfile 和兼容性。PDF 主库与 worker 版本必须一致。不要一次执行强制大升级，也不要只隐藏 npm 告警。

**验收**：相关 high 告警消除或有明确且可复核的暂缓原因；PDF 加载、文字选区、标注、缩放与 Markdown 编辑/属性解析回归通过；重新打包并做 Windows 回归后再扩大分发。

### P1-A：从真实启动测量切入前端性能

**已确认的剩余开销**：
- `src/core/documentRepository.ts` 同步解析/写入整个 `aster.documents` localStorage；`asterCore.ts` 的 `replaceAll` 会触发全量保存。
- `src/ui/App.tsx` 启动后加载 SQLite 文献再替换 store；首屏缓存和数据库数据之间仍有重复工作。
- `LibraryScene.tsx` 对全部可见文献直接渲染行，尚未做列表虚拟化。
- `project_commands.rs` 的目录枚举/Markdown 读取仍是同步原生命令；文献库 PDF 的 `load_paper_file_bytes` 也仍同步，而通用文件资源字节读取已有异步命令。

**建议任务**：先记录“进程启动→窗口显示→首屏→可交互→文献加载完成”，并记录 >50ms 前端长任务及各原生命令耗时。区分无恢复标签/恢复 Markdown/恢复大 PDF，区分首次迁移与后续启动。

再按测量结果处理：桌面端缓存职责与容错 → 文献列表虚拟化 → 尚存的同步文件读取 → 按需加载重组件。缓存调整必须保留浏览器预览与旧缓存迁移/恢复路径，不能直接删除用户缓存。

**验收**：同机同数据测试冷/热启动；保留样本数、单次值、中位数和尾部值，大样本再报告 P95。验证 100/1000/10000 文献规模。虚拟化不能改变全量筛选、批量选择和导出集合；先建立基线，再约定目标，不预先承诺“秒开”。

### P1-B：补全文献库日常使用闭环

优先顺序：导入幂等与失败清理 → 元数据编辑 → 批量标签/移动/删除的部分失败反馈 → 搜索/导出一致性 → 原位操作与键盘可用性。

**具体风险点**：`library_import.rs` 先检查重复再复制文件，并使用 `INSERT OR REPLACE`。普通 UI 导入默认生成 UUID，不能据此断言普通导入必然覆盖旧文献；但应专项测试并发重复导入、显式复用已有 paperId、复制成功而数据库写入失败等边界。

**验收**：同文件/同 DOI 去重不破坏原笔记、标注、收藏/已读及目录；失败不留下错绑附件；批量操作清楚显示哪些成功、哪些失败且可重试；CSV/Markdown/BibTeX 对中文、引号、换行和特殊字符做实际输出测试，不只检查函数名存在。

### P1-C：完善双链，但暂不做关系图

**证据**：`src/core/wikiLinks.ts` 已有文件级解析、歧义/越界保护；带 `#` 的标题/块定位明确不支持，缓存仅限单次解析，较大项目会受扫描上限限制。

**建议拆分**：先标题定位与反向链接 → aliases 检索 → 重命名引用更新。块引用和大型库增量索引后续再单独安排。

**验收**：中文、同名、相对路径、缺失目标、外部编辑都有明确行为；批量重写引用必须预览变更并支持失败回退，不能损伤 frontmatter、BOM、换行或正在编辑的缓冲。不要通过顺手实现关系图扩大范围。

### P2：收敛架构与测试流程，而不是再造框架

- `App.tsx` 当前约 3425 行。沿用已有 core/platform/features/workbench 分层，逐步提取导入协调、文献动作、工作台恢复等职责；不要在修一个交互时同时重写整个 App。
- 已有静态接线断言能防止入口断开，但不能替代点击/输入、渲染结果、失败恢复测试。把前轮隔离 UI 检查逐步固化为可复跑的测试，并保留 Windows WebView2 人工验收清单。
- 旧主开发方案/README 仍有 CLI、通用工作台、同步等扩展主线；应在用户确认后统一成“本地文献库 + Markdown + Reader 优先”。本报告不擅自改写长期产品方向。
- 交接历史很长，后续将“当前状态/下一步”与历史日志分层，避免旧的“未打包/待确认”被误当作当前事实。
- 后续发布记录建议补充源码版本、dirty 状态/补丁摘要、lockfile 校验和测试报告。现有 `build-info.json` 的 EXE/安装包 SHA-256 继续保留。

## 四、建议直接按这个顺序开展

| 批次 | 主要工作 | 出口条件 |
|---|---|---|
| 0：本次交付 | 打包当前已验证源码，使用可信测试文档做桌面验收 | 文件校验通过；记录尚未验收项，不把打包成功等同于可公开发布 |

| 4：功能完善 | 文献库批量操作/元数据，再做双链增强 | 每项有完整“操作→落库→重启→导出”验收 |

每个开发任务尽量控制为一个可验证的小改动。关系图、社区/社交、云同步扩展及额外 AI 能力继续暂缓；这不是放弃长期方向，而是避免在本地数据与交互尚未稳定时扩大维护面。
