# Aster 通用知识工作台目标文档

## 1. 产品定位

Aster 是一个本地优先、可扩展的通用知识工作台。它不只服务科研文献管理，也服务学习记录、知识库构建、项目资料整理、目录体系构建、资料阅读、笔记沉淀和 AI 辅助处理。

科研文献是 Aster 的重要核心场景，但不是唯一场景。Aster 的更大定位是：帮助用户把不同来源的信息对象组织起来，通过链接、标签、目录、笔记、标注和 AI 对话建立可查找、可复用、可扩展的个人知识系统。

核心目标是建立一套统一的信息关联系统。无论文献、PDF、网页摘录、Markdown 笔记、项目资料、课程记录、AI 对话还是后续插件贡献的数据，都应该能通过统一关系链快速关联、查找和处理。

当前最重要的产品方向有五个：

- 做到接近 Zotero 的 PDF 阅读、标记和标注能力。
- 做到接近 Obsidian 的文档、笔记、链接和知识关联管理能力。
- 做到可接入真实 AI 的本地/远程 Provider 能力。
- 做到高自由度、可持续扩展的插件系统。
- 做到可按使用场景切换工作界面，但底层信息关系保持统一。

界面设计必须服务这些能力：不是做静态展示页，而是提供一个能长期承载文献库、阅读器、笔记网络、AI 工作区、目录构建和插件扩展的专业知识工作界面。

## 2. 目标用户

- 大学生、研究生和科研学习者。
- 需要阅读论文、整理文献、做课程项目或科研训练的用户。
- 需要构建个人知识库、课程知识库、项目资料库或主题研究库的用户。
- 希望本地保存资料，不希望所有文档和笔记都依赖云服务的用户。
- 后续也面向需要 AI 辅助阅读、总结、整理和知识关联的知识工作者。

界面风格要求：

- 现代、简洁、低线条刺激。
- 信息密度要高，减少大面积空白。
- 阅读场景优先给 PDF 或正文内容留空间。
- 避免“演示样品感”，所有可见入口尽量对应真实功能。
- 功能复杂时不能靠堆按钮解决，应使用场景、抽屉、命令面板、右键菜单、快捷键和可折叠工具栏组织复杂度。
- 插件贡献的命令、视图、AI Provider、元数据源和设置项都要能自然出现在界面中，不破坏主工作流。

## 3. 核心设计原则

### 3.1 知识对象是主实体

Aster 的底层不应只理解“文献”，而应理解更通用的“知识对象”。文献是知识对象的一种。

知识对象可以包括：

- 文献
- PDF 文件
- Markdown 笔记
- 主题页面
- 项目页面
- 课程记录
- 网页摘录
- 图片或图表
- AI 对话片段
- 标注和摘录
- 后续插件贡献的数据对象

每个知识对象都应有稳定 ID，并支持：

- 标题
- 类型
- 标签
- 目录位置
- 元数据
- 关联对象
- 附件文件
- 笔记内容
- 创建和更新时间

### 3.2 统一信息关联系统

Aster 的核心不是单个功能，而是信息之间的关系。

必须支持：

- 文献与 PDF 的绑定。
- PDF 与标注的绑定。
- 标注与笔记摘录的绑定。
- 笔记与笔记的双链。
- 目录与知识对象的组织关系。
- 标签与对象的索引关系。
- AI 对话与文献、笔记、标注、任务的绑定。
- 插件数据与核心对象的受控关联。

用户应该能从任意对象顺着关系链找到相关内容，例如：

- 从文献找到原文、译文、标注、笔记和 AI 对话。
- 从笔记摘录回跳 PDF 页码和标注位置。
- 从主题笔记找到相关文献、课程记录和项目资料。
- 从 AI 对话找到当时使用的上下文。

### 3.2.1 关系系统架构设计原则

统一关系系统是 Aster 最重要的底层能力之一。它必须支持当前文献工作流，也要能扩展到笔记、项目、课程、网页摘录、AI 对话、插件数据和未来更多复杂场景。

核心原则：

- 对象和关系分离：对象负责“是什么”，关系负责“它和什么有关”。
- 稳定 ID：所有可关联对象必须有稳定 ID，不能依赖标题、路径或临时前端状态。
- 类型可扩展：对象类型和关系类型不能写死在前端页面里，插件和后续模块可以注册新类型。
- 关系有方向但可双向查询：例如“标注摘录自 PDF”有方向，但用户需要从 PDF 找标注，也需要从标注回跳 PDF。
- 关系可携带元数据：例如页码、PDF 坐标、摘录范围、AI 上下文、创建来源、置信度。
- 核心关系受控写入：插件和 AI 不能随意直接改 SQLite，必须通过受控 API 创建、更新和删除关系。
- 查询优先服务工作流：关系系统不是只为了画图，而是为了回跳、筛选、推荐、整理、AI 上下文和导出。
- 兼容现有文献表：当前 `papers`、`paper_files`、`notes`、`annotations` 不推倒重来，应逐步映射到通用对象和关系层。

### 3.2.2 知识对象模型

建议中期引入通用对象表，作为 `papers` 等专用表之上的统一索引层。

建议核心字段：

```text
knowledge_objects
  id
  type
  title
  summary
  metadata_json
  source
  created_at
  updated_at
  deleted_at
```

字段说明：

- `id`：稳定对象 ID。
- `type`：对象类型，例如 `paper`、`pdf_file`、`note`、`annotation`、`excerpt`、`topic`、`project`、`course`、`web_clip`、`ai_thread`、`ai_message`、`plugin_object`。
- `title`：用于搜索、列表和关系面板展示。
- `summary`：可选摘要，用于 AI、搜索和预览。
- `metadata_json`：类型专属元数据，例如 DOI、作者、页码、文件路径、模型名、网页 URL。
- `source`：对象来源，例如 `imported_pdf`、`manual`、`ai`、`plugin:{plugin_id}`、`builtin`。
- `deleted_at`：软删除，便于撤销、恢复和关系清理。

当前专用表与通用对象的关系：

- `papers` 保留文献专属元数据，但每条 paper 对应一个 `knowledge_objects(type='paper')`。
- `paper_files` 对应 `knowledge_objects(type='pdf_file')` 或附件对象。
- `notes` 对应 `knowledge_objects(type='note')`。
- `annotations` 对应 `knowledge_objects(type='annotation')`。
- `ai_threads` 和 `ai_messages` 对应 AI 对话对象。

这样可以保留现有业务表的效率，同时让关系、搜索、目录、插件和 AI 不再只认识文献。

### 3.2.3 关系模型

建议引入通用关系表：

```text
relations
  id
  source_object_id
  target_object_id
  type
  direction
  metadata_json
  created_by
  created_at
  updated_at
  deleted_at
```

字段说明：

- `source_object_id`：关系发起对象。
- `target_object_id`：关系目标对象。
- `type`：关系类型。
- `direction`：用于区分有向、无向或系统双向关系。
- `metadata_json`：关系元数据，例如 PDF 页码、坐标、文本范围、AI 上下文片段、排序权重。
- `created_by`：来源，例如 `user`、`system`、`ai`、`plugin:{plugin_id}`。
- `deleted_at`：软删除，支持撤销和审计。

第一批关系类型建议：

- `contains`：目录、项目、课程包含某个对象。
- `attached_file`：文献或对象绑定附件。
- `has_note`：对象绑定笔记。
- `annotates`：标注属于某个 PDF 文件或页面。
- `excerpted_from`：摘录来自 PDF、网页或笔记。
- `cites`：笔记、文献或内容引用另一个对象。
- `links_to`：笔记双链或普通对象链接。
- `related_to`：用户手动建立的相关关系。
- `generated_from`：AI 结果、摘要、笔记块由某些上下文生成。
- `discusses`：AI 对话讨论某个文献、笔记、标注或项目。
- `tagged_with`：对象与标签关系；可单独用 `object_tags` 优化，但语义上属于关系。
- `derived_from`：译文 PDF、翻译内容、改写笔记来源于原对象。
- `version_of`：对象版本关系。

待确认：

- 是否允许用户自定义关系类型。
- 自定义关系类型是否需要图标、颜色、方向、说明和可见性设置。
- 标签关系是否长期保留独立表，还是统一进入 `relations`。

### 3.2.4 目录、标签和关系的边界

三者都能组织信息，但职责不同。

- 目录：表达结构和归属，适合项目、课程、主题和长期知识体系。
- 标签：表达横向索引，适合状态、领域、方法、优先级、阅读阶段。
- 关系：表达对象之间的语义连接，适合引用、来源、摘录、生成、讨论、依赖和相关。

建议规则：

- 一个对象可以在多个目录或集合中出现，但必须清楚是“引用加入”还是“真实移动”。
- 标签不承担层级结构，避免把标签墙做成复杂目录树。
- 关系链负责回答“为什么相关”和“从哪里来”，不是只给对象分组。
- 目录、标签和关系都应能作为搜索和筛选条件。

### 3.2.5 关系系统 API

所有模块都应通过统一 API 读写关系，避免每个功能直接操作多个业务表导致后续难维护。

建议前端/后端能力：

```text
create_object(type, title, metadata)
update_object(object_id, patch)
delete_object(object_id, mode)

create_relation(source_id, target_id, type, metadata)
update_relation(relation_id, patch)
delete_relation(relation_id)
restore_relation(relation_id)

get_object(object_id)
get_relations(object_id, direction, types)
get_related_objects(object_id, query)
get_relation_path(source_id, target_id, max_depth)
search_objects(query, filters)
```

API 设计要求：

- 支持事务：导入 PDF 时，创建 paper、file、note、tags、relations 必须要么全部成功，要么回滚。
- 支持批量写入：批量导入、批量标签、批量生成笔记不能逐条低效写入。
- 支持软删除和恢复：删除对象时不应立刻破坏所有关系。
- 支持来源记录：用户、系统、AI、插件创建的关系要可追踪。
- 支持权限边界：插件只能通过 API 访问授权范围内的对象和关系。
- 支持迁移：旧表数据可以逐步补齐 object 和 relation 映射。

### 3.2.6 关系系统在场景中的表现

资料库：

- 选中资料后，能看到相关笔记、标注、AI 对话、目录位置和相关对象。
- 可按目录、标签、对象类型、关系类型筛选。
- 批量操作可以创建或移除标签、目录归属和关系。

阅读器：

- 从 PDF 页面看到当前页标注、摘录、相关笔记和 AI 对话。
- 标注能一键加入笔记，并形成 `annotation -> note_block -> pdf_file` 的可回跳关系。
- 原文 PDF 与译文 PDF 独立标注，但可通过 `derived_from` 关系知道译文来源。

笔记：

- `[[双链]]` 生成 `links_to` 关系。
- 标注摘录块保存来源关系，可回跳 PDF 页码和坐标。
- 文献引用生成 `cites` 或 `references` 关系。

AI：

- AI 对话创建 `discusses` 关系，绑定到使用的上下文对象。
- AI 生成摘要、标签建议、笔记块时创建 `generated_from` 关系。
- 用户确认 AI 结果后再写入正式对象或关系。

插件：

- 插件可以注册新对象类型和关系类型。
- 插件可以贡献关系视图、筛选器、导入器和导出器。
- 插件写入关系必须声明来源和权限。

### 3.2.7 查询、索引和性能

关系系统必须能支持复杂查询，但第一版不需要直接引入图数据库。SQLite 足够支撑 MVP 和中期版本，前提是表结构和索引合理。

建议索引：

- `knowledge_objects(type)`
- `knowledge_objects(updated_at)`
- `knowledge_objects(deleted_at)`
- `relations(source_object_id)`
- `relations(target_object_id)`
- `relations(type)`
- `relations(deleted_at)`
- `(source_object_id, type)`
- `(target_object_id, type)`

查询策略：

- 常用关系一跳查询必须快，例如当前文献的 PDF、笔记、标注、AI 对话。
- 关系链查询第一版限制深度，例如 2-3 层，避免复杂图遍历拖慢界面。
- 图谱视图使用按需加载，不一次性渲染全库。
- 搜索和关系查询分层：全文搜索负责找到对象，关系查询负责解释连接。
- 大规模数据时考虑 FTS、缓存、增量索引和后台任务。

### 3.2.8 可扩展性和插件边界

插件系统要扩展关系系统，但不能破坏核心数据。

插件可扩展：

- 新对象类型。
- 新关系类型。
- 新元数据字段。
- 新导入器和导出器。
- 新关系视图。
- 新 AI Provider 对关系的生成和解释能力。

插件限制：

- 不允许直接写 SQLite 核心表。
- 不允许删除不属于授权范围的对象和关系。
- 不允许创建没有类型声明的关系。
- 不允许绕过权限读取全文、笔记或 AI 对话。
- 插件卸载后，插件创建的数据要可识别、可保留、可导出或可清理。

### 3.2.9 迁移路线

不能为了通用关系系统推倒当前文献库。建议分阶段迁移：

1. 保持现有 `papers`、`paper_files`、`notes`、`annotations` 表稳定，先修好当前文献阅读闭环。
2. 增加前端类型层：定义 `KnowledgeObject`、`Relation`、`ObjectType`、`RelationType`，但先由现有数据映射生成。
3. 增加数据库通用表：`knowledge_objects`、`relations`，写迁移脚本把现有文献、文件、笔记、标注映射进去。
4. 新功能优先写通用对象和关系 API，不再直接写死到 `paper_id`。
5. 资料库 UI 从“文献表格”升级为“对象表格 + 文献视图”。
6. 笔记双链、标注摘录、AI 上下文、目录构建接入 `relations`。
7. 插件系统只对外暴露通用对象和关系 API。

阶段性验收：

- 现有文献、PDF、标注、笔记不丢失。
- 从文献能找到原文、译文、标注、笔记、AI 对话。
- 从标注能回跳 PDF 页码和位置。
- 从笔记摘录能回跳标注和 PDF。
- AI 对话能显示使用过的上下文对象。
- 插件或后续模块能注册新对象类型而不修改核心 UI 大量代码。

### 3.3 本地优先

第一版使用 Tauri + SQLite + 本地文件库：

- 文件导入后复制到应用数据目录。
- SQLite 保存结构化数据和关系。
- 应用离线可用。
- 后续可以增加同步，但同步不是第一阶段目标。

### 3.4 场景化界面

Aster 的核心特色之一是“按工作场景切换界面”。

第一阶段主场景：

- 资料库 / 文献库
- 阅读
- 笔记 / 知识库
- AI 对话
- 设置

后续插件可以贡献新的场景，例如：

- 课程学习
- 项目资料
- 论文写作
- 复习卡片
- 数据分析
- 翻译工作流

场景切换只改变界面和工作方式，不割裂底层数据。所有场景都应共享同一套知识对象和关系系统。

场景不应被理解为固定死板的页面，而应被理解为一组默认工作区布局。用户进入某个场景时，Aster 给出适合该任务的默认视图组合；用户也可以按自己的习惯调整布局、打开额外视图、关闭不需要的面板，并保存为自己的工作区。

场景示例：

- 资料库场景：默认显示资料表格、标签墙、目录或详情抽屉。
- 阅读场景：默认显示 PDF / Markdown 主阅读区、可折叠标注/笔记/AI 面板。
- 笔记场景：默认显示 Markdown 编辑器、反向链接、关系图或目录。
- AI 场景：默认显示对话区、上下文对象、引用来源和输出结果。
- 项目或课程场景：默认显示目录、任务、资料、笔记和 AI 辅助面板。

用户调整布局后，系统应记住每个场景的工作区状态。场景是默认工作流，不是限制用户自由的边界。

### 3.5 Zotero 级 PDF 标注目标

PDF 标注是 Aster 的核心能力之一。目标不是只画几个图层，而是接近成熟文献管理软件的阅读体验。

长期目标：

- 基于真实文字选择创建高亮和下划线。
- 选中文字后弹出标注浮层，支持快速选择颜色、类型、复制、加入笔记和 AI 解释。
- 支持锁定高亮/下划线模式，连续选择文字连续标注。
- 支持高亮、下划线、批注、便签、区域框选、删除线、自由画笔、形状等工具。
- 支持颜色、标签、批注内容、页码和引用信息。
- 支持原文 PDF 和译文 PDF 独立标注。
- 支持标注列表搜索、筛选、排序、批量删除、批量改色和批量加入笔记。
- 支持从标注生成结构化阅读笔记。
- 支持从笔记摘录回跳 PDF 对应位置。
- 支持导出标注 Markdown、BibTeX 摘录，以及后续导出带标注 PDF。
- 标注交互必须稳定：不闪烁、不误滚动、不因删除或切换工具导致标注复活或丢失。

### 3.6 Obsidian 级笔记和知识关联目标

笔记不是 PDF 的附属文本框，而是长期知识库的一部分。

长期目标：

- Markdown 作为底层格式。
- 支持文献笔记、主题笔记、项目笔记、课程笔记和每日/临时笔记。
- 支持 `[[双链]]`、反向链接、标签、块引用和文献引用。
- 支持从文献、标注、AI 对话片段生成可复用笔记块。
- 支持笔记图谱、关系链查看和知识对象之间的双向跳转。
- 支持模板、属性字段和结构化 frontmatter。
- 支持本地文件夹式资料库管理，后续可扩展为 vault / workspace。

### 3.7 AI 接入目标

AI 是独立场景，也是阅读、资料库和笔记场景中的嵌入能力。

长期目标：

- 支持独立 AI 对话工作区。
- 支持阅读器内 AI 侧栏，基于当前 PDF、选中文本、标注和笔记提问。
- 支持资料库内 AI 批量整理、标签建议、摘要生成和元数据修正。
- 支持笔记内 AI 改写、总结、生成大纲和整理摘录。
- 支持目录构建、知识关联建议和关系链解释。
- 支持 Provider 接口，接入 Codex CLI、Claude Code CLI、本地模型、OpenAI API、其他兼容 API。
- AI 对话片段必须可绑定到知识对象、文献、标注、笔记或任务，不能只是一次性聊天记录。
- 用户应能清楚看到 AI 使用了哪些上下文。

### 3.8 插件和扩展系统目标

插件系统是 Aster 的长期核心能力，不是附属功能。第一阶段可以先做本地可信插件模型，但接口设计必须为高自由度扩展预留空间。

预留扩展点：

- 命令
- 事件
- 设置项
- 场景视图
- 侧栏面板
- 阅读器工具
- 笔记块和渲染器
- 知识对象类型
- 关系类型
- 元数据源 Provider
- AI Provider
- 翻译 Provider
- 检索源 Provider
- 导入/导出 Provider
- 快捷键贡献

插件可以贡献能力，但不能破坏核心资料库的数据一致性。核心 SQLite 数据修改必须通过受控 API。

### 3.9 界面承载原则

界面设计必须从一开始支持复杂能力逐步扩展。

核心界面结构：

- 左侧紧凑场景轨：资料库、阅读、笔记、AI、设置，以及后续插件贡献场景。
- 中央主工作区：当前场景的主要操作区域，阅读场景优先给 PDF 或正文内容最大空间。
- 右侧可折叠工作面板：笔记、标注、AI、详情、关系、插件面板同一时间只展开一个或少数必要面板。
- 命令面板：承载全局命令、插件命令、快捷操作。
- 上下文菜单：承载标注、笔记块、资料条目的局部操作。
- 设置中心：承载核心设置和插件设置。

设计约束：

- 不把所有功能都放在顶部工具栏。
- 不让阅读界面被侧栏和按钮挤压。
- 插件新增能力时，必须有统一入口和权限边界。
- 高频功能提供按钮和快捷键；低频功能进入命令面板或菜单。
- 面向大学生和知识工作者，优先清晰、稳定和可发现性，而不是复杂炫技。

### 3.10 UI、易用性和审美原则

本节用于明确 Aster 的界面审美和可用性方向。下列资料是后续 UI 开发、评审和重构时的主要参考。下一个 agent 只读本目标文档，也应能理解 Aster 的审美边界和可用性标准。

#### 3.10.0 设计参考分级

`硬约束` 是必须尽量满足的标准；`主要参考` 是判断交互质量时优先参考的资料；`风格参考` 只用于借鉴，不允许直接套用视觉风格；`架构参考` 用于工作台、插件和视图组织。

| 等级 | 资料 | 链接 | Aster 中的用途 |
| --- | --- | --- | --- |
| 硬约束 | W3C WCAG 2.2 | https://www.w3.org/TR/WCAG22/ | 可访问性、键盘可用、对比度、焦点、输入和错误提示。 |
| 硬约束 | W3C/WAI Accessibility Principles | https://www.w3.org/WAI/fundamentals/accessibility-principles/ | 以可感知、可操作、可理解、健壮作为基础要求。 |
| 主要参考 | Nielsen Norman Group: 10 Usability Heuristics | https://www.nngroup.com/articles/ten-usability-heuristics/ | 状态可见、撤销恢复、一致性、防错、减少记忆负担、极简审美。 |
| 主要参考 | IBM Carbon Design System Guidelines | https://carbondesignsystem.com/guidelines/ | 企业级工具软件的内容、可访问性、表格、表单、状态和高密度界面参考。 |
| 架构参考 | VS Code UX Guidelines | https://code.visualstudio.com/api/ux-guidelines/overview | 场景轨、侧栏、面板、命令面板、上下文菜单、插件视图、工作台扩展方式。 |

| 风格参考 | Material Design 3 | https://m3.material.io/ | 颜色系统、组件状态、可访问性和设计 token 参考。不要把 Aster 做成移动 App 风格。 |

参考资料使用原则：

- Aster 不是 Apple、Fluent、Material 或 Carbon 的换皮版本。
- 遇到冲突时，优先级是：可访问性和数据安全 > 工作流效率 > 平台一致性 > 视觉风格。
- 对 Aster 最有参考价值的是 NN/g、WCAG/WAI、Carbon 和 VS Code UX Guidelines。
- Apple / Fluent / Material 主要用于组件状态、动效、平台一致性和设计 token，不决定 Aster 的整体气质。
- 不以 Dribbble、营销站、Landing Page、视觉趋势图作为核心依据。
- 新增 UI 方案必须能说明它如何改善任务效率、可理解性、可恢复性或阅读空间，而不是只说“更好看”。

这些资料给 Aster 的核心结论是：工具软件的审美不能只追求“好看”，必须服务效率、稳定、可理解、可恢复和长期低疲劳使用。

#### 3.10.1 产品气质

Aster 的界面气质应是：

- 安静、克制、专业。
- 信息密度高，但不拥挤。
- 现代、清晰、低线条刺激。
- 像长期使用的工具，而不是展示型样品。
- 面向大学生、研究生和知识工作者，不做幼稚化、营销化、游戏化视觉。
- 允许功能强大，但复杂度要被组织起来，而不是直接堆在界面上。

不应出现：

- 大面积装饰性渐变、光斑、背景图和无功能插画。
- 过大的标题、过大的图标、过宽的按钮和过多空白。
- 只有视觉效果、没有真实功能的入口。
- 多层卡片套卡片。
- 重边框、重阴影、过多分割线。
- 用颜色作为唯一的信息表达方式。

#### 3.10.2 可用性原则

Aster 的每个功能都应满足以下可用性原则：

- 状态可见：导入、保存、同步、AI 生成、标注保存、删除、备份等动作必须有明确状态，不让用户猜测是否成功。
- 语言贴近用户：界面文案使用中文和用户熟悉的知识管理语言，避免暴露数据库、内部模型或工程术语。
- 用户可控：危险动作可撤销或确认；标注、删除、改色、移动、导入都要有恢复路径。
- 一致性：同类按钮、图标、菜单、快捷键、弹窗和抽屉行为保持一致。
- 防错优先：能预防错误就不要只依赖错误提示，例如删除前确认、导入前预览、标签去重、路径检查。
- 减少记忆负担：常用功能应可见或可通过命令面板搜索；快捷键是加速器，不是唯一入口。
- 新手和熟练用户兼容：新手能通过按钮完成任务，熟练用户能通过快捷键、命令面板和右键菜单提速。
- 审美服务任务：视觉元素必须帮助用户阅读、定位、比较、操作或理解状态；无意义装饰应删除。
- 错误可理解：错误信息必须说明发生了什么、影响是什么、下一步怎么处理。
- 帮助在上下文中出现：不要依赖大段教程，优先在导入、标注、AI、插件权限等场景给出短提示。

#### 3.10.3 信息架构原则

Aster 承载的对象会很多，信息架构必须清楚。

- 资料库负责对象集合、搜索、筛选、标签、目录和批量操作。
- 阅读场景负责 PDF / Markdown 阅读、标注、摘录、阅读笔记和 AI 辅助。
- 笔记场景负责 Markdown、双链、反向链接、知识图谱和结构化整理。
- AI 场景负责对话、上下文、引用来源和生成结果落库。
- 设置场景负责软件行为、快捷键、插件、Provider、资料库路径、备份和诊断。

界面优先级：

1. 当前主任务内容，例如 PDF、Markdown、资料表格。
2. 与当前任务直接相关的工具，例如标注工具、标签、搜索。
3. 当前对象的上下文，例如笔记、标注列表、关系、AI。
4. 低频管理能力，例如设置、插件权限、导出、迁移。

低频功能不应占用长期可见空间，应进入命令面板、右键菜单、更多菜单、设置或可折叠面板。

#### 3.10.4 视觉审美原则

Aster 的视觉方向是“克制的专业工具”，不是“强品牌展示页”。

颜色：

- 主色只用于当前选中、主要操作和焦点状态。
- 功能色必须语义清晰：成功、警告、错误、信息、标注颜色分开。
- 禁止整页被单一色系支配，尤其避免过度紫蓝、深蓝、棕橙、米黄等一眼主题化的方案。
- 标注颜色需要足够区分，但透明度要适合阅读，不能压住文字。
- 不只用颜色表达状态，必须配合图标、文本、形状或位置。

字体和层级：

- 基础字号以 13-14px 为主，适合桌面高密度工具。
- 场景标题清晰但不夸张，说明文字必须比标题弱。
- 表格、工具栏、抽屉、设置项使用紧凑但可读的字号。
- 不使用随视口宽度变化的字体大小。
- 中文界面优先保证字重、行高、间距稳定，避免发虚和拥挤。

空间和密度：

- 采用 4px / 8px 的间距节奏。
- 阅读场景优先把空间留给 PDF 或正文。
- 资料库优先使用表格、列表、树、标签墙等高密度结构。
- 卡片只用于重复条目、弹窗或需要明显分组的内容，不把页面整体做成一堆大卡片。
- 分割线尽量弱化，优先用间距、背景层级和轻量边框建立结构。

形状和控件：

- 常规圆角保持 6-8px，不使用过度圆润的胶囊风格泛滥。
- 图标按钮用于工具栏、场景轨和标注工具；文字按钮用于明确命令。
- 按钮大小应服务操作效率，不因视觉风格占用过多空间。
- 可点击区域必须足够，但视觉外形可以紧凑。
- 工具栏图标必须有 tooltip，并在需要时显示快捷键。

动效：

- 动效只用于状态变化、展开折叠、定位和反馈。
- 不做持续吸引注意力的装饰动画。
- 标注、删除、切换工具、页面跳转不能造成 PDF 闪烁、重载或滚动跳位。
- 所有动效应短、轻、可关闭或不影响操作。

#### 3.10.5 可访问性和键盘原则

Aster 长期应以 WCAG AA 作为桌面 Web UI 的基础参考。

必须做到：

- 所有核心功能可以通过键盘完成。
- 焦点状态清晰可见。
- 文字与背景对比度达标。
- 控件有可理解的名称，图标按钮必须有 tooltip 和可访问标签。
- 不把颜色作为唯一信息来源。
- 文本放大或界面密度调整时不遮挡关键内容。
- 输入框、弹窗、抽屉和菜单的焦点顺序合理。
- `Esc` 能退出临时状态，例如菜单、弹窗、选择、标注工具的临时编辑。
- `Ctrl+Z` / `Ctrl+Y` 等快捷键行为稳定，不因焦点位置造成危险误操作。

#### 3.10.6 工作流易用性原则

核心工作流必须做到“少步骤、可确认、可恢复”。

资料导入：

- `从 PDF 导入` 是明显主入口。
- 自动提取只生成草稿，不强迫用户相信机器结果。
- 用户可以直接确认，也可以修改标题、作者、标签等字段。
- 导入后立即能在资料库看到，并能进入阅读。

阅读标注：

- 默认鼠标是浏览工具，不误创建标注。
- 高亮和下划线基于真实文字选择。
- 标注保存后持续显示。
- 删除、撤销、重做稳定。
- 标注工具不应导致页面跳动。

笔记关联：

- 从标注到笔记的路径要短。
- 笔记中的摘录应能回跳 PDF。
- 文献、笔记、标注、AI 对话之间的关系要可见。

AI 使用：

- 用户能清楚看到 AI 使用了哪些上下文。
- AI 输出默认不应直接改写用户资料，除非用户确认。
- AI 结果应能保存为笔记、摘录、标签建议或关系建议。

#### 3.10.7 UI 验收检查清单

每次新增或重做界面时，需要检查：

- 这个入口是否对应真实功能。
- 用户能否看出当前状态。
- 是否支持取消、撤销或恢复。
- 是否有键盘路径。
- 是否有明确焦点状态。
- 是否能在小窗口下正常使用。
- 是否会挤压阅读主内容。
- 是否出现过大的标题、图标、按钮或空白。
- 是否有多余说明文字、装饰图形或重复信息。
- 是否把低频功能放到了长期可见位置。
- 是否符合当前场景的信息优先级。
- 是否和已有按钮、菜单、快捷键、抽屉行为一致。
- 是否会造成 PDF 闪烁、重载、滚动跳位或输入丢失。
- 是否能让第一次使用的人完成任务，同时不拖慢熟练用户。

#### 3.10.8 场景级设计分配

不同场景的界面不能只是换标题和按钮，而应该围绕该场景的主任务重新分配空间、工具和上下文。所有场景共享同一套工作台框架，但主内容、右侧面板、工具栏、快捷键和命令面板入口应按场景调整。

##### 全局工作台外壳

所有场景共享：

- 左侧紧凑场景轨：只放图标和 tooltip，不放大字母和无关品牌装饰。
- 中央主工作区：永远给当前主任务最大空间。
- 右侧可折叠工作面板：承载笔记、标注、AI、详情、关系、插件视图。
- 顶部或场景内工具条：只放当前场景高频操作。
- 命令面板：承载全局命令、低频命令和插件命令。
- 上下文菜单：承载对象局部操作，例如改标签、删除、加入笔记、AI 解释。
- 状态区：轻量展示保存、同步、索引、AI Provider、资料库路径等状态。

全局外壳原则：

- 左侧场景轨保持窄，目标宽度约 44-52px。
- 顶部区域尽量一行完成，不做大标题横幅。
- 场景标题可以存在，但不得比主内容更抢眼。
- 右侧面板默认按需展开，阅读场景默认收起。
- 所有面板都应可关闭或折叠，并能恢复默认布局。
- 插件视图必须进入统一工作台区域，不允许破坏主布局。

##### 资料库 / 文献库场景

主任务：导入、查找、筛选、整理和批量处理资料。

默认布局：

- 中央：高密度资料表格。
- 右侧：标签墙 / 筛选器 / 可切换详情抽屉。
- 顶部工具区：搜索、`从 PDF 导入`、批量操作入口、视图切换。
- 左侧不默认显示复杂目录树，除非进入“目录管理”或用户打开目录视图。

设计要求：

- `从 PDF 导入` 必须是明显主按钮。
- 表格优先展示标题、作者、年份、来源、标签、状态等可比较信息。
- 标签以 chip 展示，不能使用逗号字符串作为主要交互。
- 批量操作只在选中对象后出现，避免常驻占空间。
- 空状态必须引导真实操作，不放营销式说明。
- 右侧标签墙适合快速过滤，但不能挤压表格到不可读。
- 资料详情不应长期占据首页主区域，优先使用右侧抽屉或独立详情视图。

适合的控件：

- 表格、紧凑搜索框、标签 chip、筛选菜单、批量操作条、右键菜单、详情抽屉。

不适合：

- 大卡片瀑布流作为默认文献列表。
- 大面积欢迎页。
- 只展示绑定 ID、文件数量等内部信息。

##### 阅读场景

主任务：长时间阅读 PDF / Markdown、标注、摘录、写笔记、询问 AI。

默认布局：

- 中央：PDF 或 Markdown 主阅读区。
- 顶部轻量工具条：文件切换、内容模式、缩放、页码、布局、更多。
- 阅读区附近：紧凑图标标注工具栏。
- 右侧：单抽屉面板，内部 tab 为笔记、标注、AI、详情、关系。

设计要求：

- PDF / Markdown 内容必须拥有最大空间。
- 阅读场景不显示大段说明文字。
- 顶部控件不能超过一行，低频功能进入更多菜单或命令面板。
- 标注工具用图标按钮，必须有 tooltip 和快捷键提示。
- 默认鼠标工具是浏览，不误创建标注。
- 高亮和下划线基于真实文字选择，不做自由划线替代。
- 标注创建、删除、改色、撤销不能导致页面跳动、闪烁、重载。
- 原文和译文切换要清楚，但不占大块空间。
- 进度显示要轻量，不使用明显占位的粗滚条或大进度条。
- 右侧面板同一时间只展开一类内容，避免 PDF 被挤压。

适合的控件：

- 图标工具栏、分段控件、轻量页码输入、缩放按钮、可折叠抽屉、标注列表、浮层编辑器、上下文菜单。

不适合：

- 阅读器顶部大标题和大说明。
- 多个右侧面板同时常驻。
- 标注保存成功 toast 高频弹出干扰阅读。
- 标注工具使用大文字按钮长期占据空间。

##### 笔记 / 知识库场景

主任务：写作、整理、链接、回顾和构建知识结构。

默认布局：

- 中央：Markdown 编辑器或阅读预览。
- 左侧可选：目录 / 笔记列表 / 最近打开。
- 右侧：反向链接、关系、属性、相关标注、AI 辅助。
- 顶部：当前笔记标题、保存状态、模式切换、更多操作。

设计要求：

- Markdown 是底层格式，编辑体验可以逐步增强。
- 支持编辑、预览、实时预览或所见即所得的模式切换。
- `[[双链]]`、标签、属性和引用块要在编辑体验中自然出现。
- 文献摘录、PDF 页码、标注引用必须能回跳来源。
- 右侧关系和反链面板应服务当前笔记，不要做装饰性图谱。
- 笔记场景需要比阅读场景更适合分屏，例如左边笔记、右边 PDF 或 AI。

适合的控件：

- Markdown 编辑器、标题输入、属性面板、反向链接列表、关系面板、命令面板、模板菜单。

不适合：

- 把笔记只做成文献的附属小文本框。
- 默认强制富文本私有格式。
- 图谱优先于真实编辑和链接能力。

##### AI 对话场景

主任务：围绕资料、笔记、标注和目录进行问答、整理、总结和生成。

默认布局：

- 中央：对话流。
- 右侧：当前上下文对象、引用来源、可保存结果。
- 顶部：Provider、模型、上下文范围、会话管理。
- 底部：输入框、附件/上下文选择、发送和停止。

设计要求：

- 用户必须能看到 AI 使用了哪些上下文。
- AI 输出不能默认直接修改资料，必须提供确认操作。
- 回答中的引用来源、文献、标注、笔记应可点击回跳。
- AI 结果可保存为笔记、摘录、标签建议、目录建议或关系建议。
- Provider 状态必须清楚：未配置、可用、运行中、失败。
- AI 对话既是独立场景，也可以作为阅读、资料库、笔记中的右侧面板。

适合的控件：

- 对话气泡、上下文 chip、引用卡片、保存为菜单、Provider 切换、停止生成按钮、错误重试。

不适合：

- 只有一个孤立聊天框，无法绑定知识对象。
- AI 自动大量改写用户资料。
- 隐藏上下文来源。

##### 目录 / 关系场景

主任务：构建知识结构、查看对象关系、从一个对象找到相关对象。

默认布局：

- 中央：目录树、关系链列表或图谱视图。
- 左侧可选：对象类型和目录过滤。
- 右侧：选中对象详情、相关对象、操作建议。

设计要求：

- 目录和标签职责要区分：目录偏结构，标签偏索引。
- 关系图不能只是装饰；必须支持定位、筛选、跳转和解释关系。
- 第一版可以优先做关系链列表和目录树，不急于做复杂图谱。
- 用户应能从文献、标注、笔记、AI 对话跳到关系视图。

适合的控件：

- 树、列表、关系链、面包屑、对象详情抽屉、筛选器、轻量图谱。

不适合：

- 默认全屏复杂节点图，无法操作。
- 只显示漂亮连线，不提供实际跳转和管理能力。

##### 设置场景

主任务：管理软件行为、资料库、快捷键、插件、Provider、备份和诊断。

默认布局：

- 左侧：设置分类。
- 中央：设置项表单。
- 右侧可选：说明、风险提示或诊断信息。

设计要求：

- 设置页应支持搜索。
- 危险设置需要确认和说明影响。
- 插件设置、Provider 设置、快捷键设置要进入统一设置中心。
- 路径、备份、恢复、导出等操作要有清晰状态和错误提示。
- 不把设置做成展示卡片墙，应保持表单和列表效率。

适合的控件：

- 设置分组、搜索框、开关、选择器、路径输入、危险操作区、诊断信息表。

不适合：

- 大量装饰卡片。
- 把重要状态藏在二级弹窗里。

##### 插件视图和插件贡献界面

主任务：让插件能力自然进入工作台，同时保持边界和一致性。

设计要求：

- 插件贡献的视图必须声明类型、标题、图标、默认停靠位置和权限。
- 插件视图默认使用 Aster 的基础控件和主题 token。
- 插件命令进入命令面板，可以绑定快捷键。
- 插件设置进入设置中心。
- 插件权限必须可见。
- 插件异常时可以禁用，不影响核心资料库。

适合的控件：

- 插件视图容器、权限说明、设置贡献、命令面板入口、错误边界。

不适合：

- 插件私自创建完全不同风格的主界面。
- 插件绕过受控 API 直接改核心数据。

#### 3.10.9 设计系统落地要求

为了让不同 agent 和协作者保持一致，Aster 需要逐步形成自己的轻量设计系统，而不是每个页面单独写样式。

基础 token：

- 颜色 token：背景、表面、表面悬停、边框、弱边框、文本、弱文本、主色、焦点、错误、警告、成功、信息、标注色。
- 字号 token：正文、弱说明、表格、按钮、标题、场景标题。
- 间距 token：4px / 8px / 12px / 16px / 24px。
- 圆角 token：小控件、常规控件、弹窗。
- 阴影 token：尽量少，只用于弹窗、浮层和临时菜单。
- 层级 token：场景轨、工具栏、抽屉、弹窗、命令面板、toast。

基础组件：

- 场景轨按钮。
- 图标按钮和 tooltip。
- 主按钮、次按钮、危险按钮。
- 表格、列表、树。
- 标签 chip 和标签输入器。
- 抽屉、弹窗、菜单、上下文菜单。
- 分段控件、tab、面板标题栏。
- 搜索框、筛选器、空状态。
- toast / inline status。
- 命令面板。
- 快捷键显示组件。

实现原则：

- 优先复用现有组件和 token，不在单个页面写一次性样式。
- 新组件必须同时考虑 hover、active、focus、disabled、loading、error 状态。
- 图标按钮必须有 tooltip 和可访问标签。
- 所有弹窗必须有关闭、取消或明确的完成动作。
- 所有危险动作必须可恢复或二次确认。
- 组件视觉密度要适合桌面工具，不按移动端组件尺寸设计。

#### 3.10.10 当前设计结论

当前最适合 Aster 的整体方向是：

- 结构上参考 VS Code / Obsidian：场景轨、工作台、命令面板、可折叠面板、后续标签页和分屏。
- 视觉上参考 Carbon 类型的专业工具：高密度、克制、清楚、表格和表单能力强。
- 交互底线参考 NN/g 和 WCAG：状态明确、可撤销、防错、键盘可用、错误可理解。
- Apple / Fluent / Material 只作为局部控件、动效和平台一致性的参考。

这意味着 Aster 的界面应该是：

- 安静但不简陋。
- 专业但不压抑。
- 高密度但不拥挤。
- 功能丰富但不堆按钮。
- 可扩展但默认好用。
- 适合长时间阅读、写作、整理和 AI 辅助工作。

这也意味着 Aster 不应该是：

- 营销网站式大标题和大插图。
- 移动 App 式大圆角、大卡片、大按钮。
- 纯工程 IDE 式过暗、过硬、过多面板。
- 视觉样品式只有布局，没有真实工作流。

### 3.11 自由工作台和可组合布局

Aster 的界面长期目标应接近 Obsidian / VS Code 的工作台自由度，但第一版不能为了自由度牺牲稳定性。正确方向是“默认好用 + 可逐步解锁自由布局”。

核心概念：

- `Scene`：场景，代表一组默认工作流和默认布局。
- `View`：视图，例如资料表格、PDF 阅读器、Markdown 编辑器、标注列表、AI 对话、关系图、目录树、标签墙、对象详情。
- `Panel`：承载视图的面板，可以位于左侧、右侧、底部或中央。
- `Pane`：中央工作区中的分屏区域，可以横向或纵向拆分。
- `Tab`：同一个面板或分屏内可以打开多个对象或视图。
- `WorkspaceLayout`：用户保存的布局状态，包含场景、面板位置、分屏比例、打开的视图、激活标签和折叠状态。

长期需要支持的布局能力：

- 面板可展开、折叠、调整宽度和关闭。
- 中央工作区支持标签页。
- 中央工作区支持左右分屏和上下分屏。
- PDF、Markdown、AI、关系图、资料详情可以并排打开。
- 右侧面板支持在笔记、标注、AI、详情、关系之间切换。
- 用户可以保存和恢复布局，例如“专注阅读”“边读边记”“AI 辅助阅读”“写作整理”“课程复习”。
- 支持重置为默认布局，避免用户把界面调乱后无法恢复。
- 支持命令面板打开任意视图，例如“打开标注列表”“在右侧打开 AI”“左右分屏打开笔记”。
- 插件可以贡献 View、Panel、Command、快捷键和默认停靠位置。

第一阶段不做完全自由拖拽布局，但必须避免把 UI 写成不可扩展的固定页面。MVP 可以按以下层级推进：

1. 固定场景布局 + 可折叠右侧工作面板。
2. 可调整宽度的左右面板 + 中央标签页。
3. 中央工作区支持左右/上下分屏。
4. 每个场景保存用户布局。
5. 插件贡献视图并停靠到指定区域。
6. 更接近 VS Code / Obsidian 的拖拽停靠和命令驱动布局。

布局系统的约束：

- 默认布局必须足够好，新用户不需要先配置才能使用。
- 阅读场景始终优先保证 PDF 或正文空间。
- 面板不能随意覆盖主要内容，除非是临时弹层。
- 布局状态只保存界面结构，不直接保存业务数据。
- 插件视图必须通过统一注册接口进入工作台，不能绕过主界面私自创建窗口或破坏数据。

### 3.12 从文献库到通用知识对象的过渡原则

当前代码和数据库已经以 `papers`、`paper_files`、`notes`、`annotations` 为主线实现了第一版文献工作流。这个闭环不能推倒重来，应继续作为最先可用、最先打磨稳定的核心场景。

但从现在开始，新增能力需要遵守以下过渡原则：

- 短期继续保证文献导入、PDF 阅读、标注、笔记和 AI 对话稳定可用。
- 中期在现有文献模型之上抽象 `KnowledgeObject` 和 `Relation` 概念。
- 新功能如果不只服务文献，应避免命名、接口和 UI 只绑定 `paper`。
- 标签、目录、笔记、AI 对话、插件数据和关系链应逐步迁移到通用对象层。
- 文献可以继续作为一种重要的知识对象类型，而不是被废弃。
- 旧数据迁移必须可控，不能因为架构调整破坏用户已经导入的 PDF、标注和笔记。

建议的演进顺序：

1. 保持当前 `papers` 工作流稳定，先修好 PDF 标注、删除、撤销、便签和笔记联动。
2. 增加通用对象层的类型定义和前端状态模型，让 UI 能理解“文献、笔记、主题、项目资料”等对象类型。
3. 在数据库中逐步引入 `knowledge_objects`、`relations`、`object_tags` 等通用表，并通过迁移兼容现有 `papers`。
4. 把文献库扩展为资料库，让文献只是默认视图之一。
5. 让插件、AI Provider、笔记双链和目录系统都接入统一对象关系模型。

## 5. 当前已实现的能力

### 5.1 资料库 / 文献库

当前资料库首先以文献库形态实现，目标是做成真实可用的高密度表格界面。

已实现方向：

- 从 PDF 导入文献。
- 导入后复制 PDF 到本地资料库。
- 从 PDF/文件名生成标题和作者草稿。
- 用户可确认或修改元数据。
- 标签 chip 输入，回车新建标签。
- 已有标签自动提示。
- 空标签兜底为“未分类”。
- 表格展示文献。
- 右侧标签墙过滤。
- 批量标签、批量删除。
- 复制 Markdown / CSV / BibTeX。
- 手动导入译文 PDF 并绑定到原文文献。

后续需要继续完善：

- 从“文献库”扩展为更通用的“资料库”。
- 支持更多知识对象类型，不只文献。
- 支持目录树、文件夹、集合和自定义视图。
- 元数据提取准确性。
- Crossref / arXiv / DOI 在线补全。
- 重复文献检测和合并。
- 文献/资料详情抽屉。

### 5.2 阅读器和 PDF 标注

当前阅读器目标是能稳定阅读 PDF，并逐步接近 Zotero 的标注体验。

已实现方向：

- PDF.js 多页连续阅读。
- 原文 PDF / 译文 PDF 切换。
- Markdown 阅读模式。
- 缩放和页码跳转。
- 高亮、下划线、区域框选、批注、便签。
- 预设颜色和自定义颜色。
- 原文/译文独立标注系统，按 `file_id` 隔离。
- 标注删除。
- 键盘删除：`Delete` / `Backspace`。
- 取消选中：`Esc`。
- 撤销/重做：`Ctrl+Z`、`Ctrl+Y`、`Ctrl+Shift+Z`。
- 删除后通过后端 `restore_annotation` 按原 ID 恢复。
- 点击 PDF 内标注不应触发页面自动滑动。

后续需要继续完善：

- 选中文字后弹出高亮/下划线浮层。
- 锁定高亮/下划线工具，连续选择文字连续标注。
- 右键菜单删除、改色、复制、加入笔记。
- 标注列表搜索、筛选、批量操作。
- 标注一键生成笔记。
- 笔记中的摘录回跳 PDF。
- 便签直接在 PDF 上编辑。
- 便签调整大小、折叠和展开。
- 导出带标注 PDF。
- 扫描版 PDF 的 OCR 支持。

### 5.3 笔记和知识库

当前笔记采用 Markdown 为底层格式。

已实现方向：

- 每篇文献绑定 Markdown 笔记。
- 阅读场景右侧抽屉编辑笔记。
- 支持编辑和预览。
- 标注可以追加到笔记。

后续需要继续完善：

- 更接近 Obsidian 的编辑体验。
- 知识对象、笔记、标注之间的双向链接。
- 引用块、摘录块、页码链接。
- 从全部标注生成结构化阅读笔记。
- 支持主题笔记、项目笔记、课程笔记和文献笔记之间的链接网络。
- 支持反向链接、标签面板和关系视图。
- 支持目录构建和知识库结构化管理。

### 5.4 AI 对话和 AI Provider

当前 AI 对话先作为独立场景和阅读侧栏入口的基础容器。

已实现方向：

- AI 对话场景。
- 当前文献上下文绑定。
- 对话记录写入本地数据库。
- 预留 Provider 接入。

后续需要继续完善：

- Codex CLI 接入。
- Claude Code CLI 接入。
- 本地模型 Provider。
- OpenAI API 或兼容 API Provider。
- 文献问答、总结、翻译、笔记整理。
- 资料库整理、目录建议和知识关系建议。
- AI 对话片段绑定到知识对象、文献和标注。
- AI 在阅读器、资料库、笔记编辑器中作为嵌入能力出现，而不只在独立对话页。

### 5.5 插件和扩展

插件系统是后续架构重点。

第一阶段目标：

- 建立命令注册、事件监听、设置贡献和 Provider 接口的基础约定。
- 支持本地可信插件，不做插件市场。
- 插件可以贡献 AI Provider、元数据源、翻译源、导入导出能力和简单视图。

长期目标：

- 类似 Obsidian / VS Code 的扩展自由度。
- 插件可以贡献知识对象类型、关系类型、场景、侧栏、命令、快捷键、设置页和阅读器工具。
- 插件权限可见、可管理。
- 插件不能直接破坏核心 SQLite 数据，需要通过受控 API 修改资料库。

## 6. 主要功能范围清单（审阅版）

本章节用于确认 Aster 需要实现的主要功能范围。标记含义：

- `P0`：当前阶段必须优先完成，否则软件难以形成稳定可用闭环。
- `P1`：核心能力，P0 稳定后应继续实现。
- `P2`：长期增强能力，可以后移。
- `明确`：方向已经确定。
- `待确认`：需要进一步确认范围、优先级或具体交互。

### 6.1 资料库 / 知识对象管理

- `P0 / 明确` 本地资料库初始化：创建 SQLite 数据库、文件库目录、默认指南文档。

## 7. 产品阶段规划

### Phase 1：本地资料库可用

目标：用户可以真实导入 PDF、管理文献/资料、打标签、打开阅读器，并拥有稳定的默认工作区布局。

完成标准：

- PDF 能导入并复制到本地资料库。
- 文献/资料能显示在表格中。
- 标签能创建、过滤、编辑。
- 译文 PDF 能绑定。
- 数据能持久化到 SQLite。
- 阅读、资料库、AI、设置等场景有清晰入口。
- 右侧工作面板可以折叠，阅读场景不被固定侧栏挤压。
- 用户的基础布局偏好可以保存，例如默认阅读布局、右侧面板开合状态和界面密度。

### Phase 2：Zotero 级阅读和标注基础

目标：用户可以稳定阅读 PDF，并获得接近 Zotero 的核心标注体验。

完成标准：

- PDF 显示清晰、缩放稳定。
- 高亮/下划线基于文字选择。
- 批注和便签不会丢失。
- 删除、键盘删除、撤销/重做稳定。
- 原文和译文标注互不混用。
- 标注能加入笔记。
- 选中文字后可以快速高亮/下划线/批注。
- 标注列表可以搜索和筛选。

### Phase 3：Obsidian 级笔记和知识联动

目标：从“能读”变成“能沉淀知识”，并形成资料、标注、笔记之间的长期知识网络，同时让工作台具备基础自由布局能力。

完成标准：

- 标注列表可搜索、筛选、批量处理。
- 一键从标注生成阅读笔记。
- 笔记内摘录可回跳 PDF。
- 支持双链、反向链接、标签和引用块。
- 支持文献笔记、主题笔记、项目笔记、课程笔记的组织方式。
- 支持目录构建和关系链查看。
- 支持中央工作区标签页。
- 支持 PDF、Markdown、AI、关系面板并排打开。
- 支持每个场景保存和恢复用户布局。
- 支持重置默认布局。

### Phase 4：AI 接入和插件化

目标：接入本地/远程 AI 能力，并形成高自由度可扩展底座和插件化工作台。

完成标准：

- AI Provider 接口稳定。
- 支持至少一个本地 CLI Provider。
- 支持文献问答、总结和笔记整理。
- 支持资料库整理、目录建议和知识关系建议。
- 翻译 Provider 接口可用。
- 元数据 Provider 可扩展。
- 插件能贡献命令、设置、侧栏视图和 Provider。
- 插件能贡献工作台视图，并声明默认停靠位置。
- 命令面板可以打开核心视图和插件视图。
- 快捷键系统可以覆盖场景、视图和插件命令。

### Phase 5：可靠性和导出

目标：让用户能长期使用和迁移数据。

完成标准：

- 资料库备份和恢复可靠。
- 导出 Markdown、CSV、BibTeX。
- 导出标注和笔记。
- 后续支持导出带标注 PDF。
- 大资料库性能稳定。

## 8. 当前优先级

近期优先级按顺序：

1. 稳定现有文献/资料库导入和本地持久化，确保用户数据不丢失。
2. 完成接近 Zotero 的 PDF 标注核心体验，优先修复删除、键盘删除、撤销/重做、标注不稳定显示、误滚动和便签丢失问题。
3. 完成原文 PDF 和译文 PDF 的独立标注系统，确保两个文件的标注互不混用。
4. 把固定界面整理成工作台骨架：可折叠面板、布局偏好保存、命令面板、快捷键入口。
5. 完成 Obsidian 式 Markdown 笔记、双链和知识对象关联。
6. 从文献库扩展为通用资料库，增加知识对象、目录构建和关系链查看。
7. 完成中央标签页和基础分屏，让 PDF、笔记、AI、关系视图可以并排使用。
8. 完成 AI Provider 接入，让 AI 能在阅读器、资料库和笔记中使用。
9. 完成插件系统基础，让核心功能可扩展，插件可以贡献命令、设置、视图和 Provider。
10. 完成标注列表搜索、筛选、批量处理和标注到 Markdown 笔记的结构化联动。

## 9. 长期规划与第一阶段边界

本节列出的能力不是被放弃，而是第一阶段不进入主线实现。当前优先级仍然是：本地资料库、PDF 阅读标注、Markdown 笔记、知识关系、AI Provider 和插件底座。长期能力需要从现在开始预留架构边界，但不能拖慢 P0 闭环。

### 9.1 云同步

长期需要。Aster 的同步必须建立在本地优先基础上，不能让用户离线不可用。

目标能力：

- 同步 SQLite 结构化数据、Markdown 笔记、PDF 文件、标注和设置。
- 支持选择性同步，例如只同步笔记和元数据，PDF 文件按需下载。
- 支持冲突检测和冲突解决，避免多设备编辑导致数据丢失。
- 支持同步状态可见：已同步、同步中、冲突、失败、仅本地。
- 支持备份和恢复，不能把同步当成唯一备份方案。

可能路线：

1. 先做本地备份和恢复。
2. 再做资料库导出 / 导入。
3. 再做单用户多设备同步。
4. 最后再考虑团队共享同步。

待确认：

- 第一批同步后端：自建服务、WebDAV、S3、Git、云盘目录，还是插件 Provider。
- 是否需要端到端加密。
- 是否允许用户只同步笔记，不同步 PDF 原文件。

### 9.2 多人协作

长期需要，但必须在单用户本地资料库稳定后再做。多人协作不是简单共享文件，而是知识对象、标注、笔记、目录和 AI 对话的协作。

目标能力：

- 共享项目资料库或课程资料库。
- 多人共同维护目录、标签、笔记和资料。
- 支持评论、任务、修改记录和贡献者信息。
- 支持权限：只读、评论、编辑、管理员。
- 支持协作中的冲突解决和历史版本。

第一阶段不做实时协同编辑。更现实的路线是先做异步协作：共享资料库、变更记录、评论和合并。

待确认：

- 协作主要面向课程小组、科研小组、论文写作，还是通用团队资料库。
- 是否需要实时多人编辑 Markdown。
- AI 对话和私有笔记是否默认不共享。

### 9.3 移动端

长期需要，但桌面端仍是主端。移动端不应一开始复制完整桌面功能，而应服务轻量阅读、检索、记录和摘录。

目标能力：

- 查看资料库、目录、标签和关系链。
- 阅读 PDF 和 Markdown。
- 查看和创建基础标注。
- 快速记录想法、拍照、网页摘录或语音转文字。
- 与桌面端同步笔记、标注和资料元数据。

待确认：

- 第一版移动端是 iOS、Android，还是先做 PWA。
- 移动端是否支持完整 PDF 标注工具。
- 是否允许移动端离线编辑后再同步。

### 9.4 插件市场

长期需要。第一阶段先做本地可信插件，不做市场；但插件接口要为市场预留元数据、版本、权限和兼容性信息。

目标能力：

- 插件发现、安装、启用、禁用、卸载和更新。
- 插件详情页展示功能、权限、版本、作者、兼容版本和更新日志。
- 插件可以按类型筛选：AI Provider、元数据源、翻译、导入导出、阅读器工具、笔记增强、主题等。
- 插件有评分、下载量或可信标识。
- 插件出问题时可以安全禁用，并提供故障诊断。

待确认：

- 插件市场是官方维护、社区仓库，还是用户自定义源。
- 插件审核机制是否需要。
- 插件是否允许收费或私有分发。

### 9.5 富文本和块编辑体验

长期需要，但底层仍应坚持 Markdown 或可导出的开放格式。目标不是把笔记锁死在私有富文本里，而是给用户更顺滑的编辑体验。

目标能力：

- Markdown 源码模式。
- 实时预览模式。
- 所见即所得模式。
- 块级编辑：段落、标题、列表、引用、代码块、图片、表格、公式、标注摘录块。
- 文献引用、PDF 页码引用、标注引用和 AI 输出块。
- 支持从 PDF 标注一键生成结构化笔记块。

待确认：

- 第一版编辑器采用 CodeMirror、ProseMirror、Lexical，还是轻量自研。
- 是否需要数据库块模型，还是继续以 Markdown 文件为主。
- 表格、公式、图片、嵌入 PDF 摘录是否第一批做完整。

### 9.6 插件沙箱和权限系统

长期需要。只要插件能访问文件、网络、AI Provider 或资料库，就必须有权限边界。第一阶段可以本地可信，但接口设计不能假设所有插件永远可信。

目标能力：

- 插件权限声明：文件、网络、数据库、AI Provider、命令、视图、剪贴板等。
- 用户安装或启用插件时能看到权限。
- 插件通过受控 API 访问资料库，不能直接破坏 SQLite。
- 插件异常不会拖垮主程序。
- 插件有资源限制和禁用机制。

待确认：

- 插件运行时采用 WebView、Node/JS 扩展宿主、独立进程，还是 Tauri 插件。
- 是否需要网络域名白名单。
- 是否需要插件签名和完整性校验。

### 9.7 完整在线论文数据库自建

优先级较低。Aster 不应在早期尝试自建完整在线论文数据库，这会显著增加成本和维护复杂度，也不是当前产品差异点。

更合理的方向：

- 通过 Provider 接入 Crossref、arXiv、Semantic Scholar、PubMed 等外部元数据源。
- 只缓存用户导入、检索或确认过的元数据。
- 不爬取和维护完整论文库。
- 不把在线论文数据库作为核心竞争点。

待确认：

- 是否需要中文论文源，例如 CNKI、万方、维普的检索或手动元数据补全。
- 是否支持用户配置自定义元数据源。
- 是否允许插件提供专业领域检索源。

## 10. 成功标准

软件达到阶段性可用时，应满足：

- 用户能导入自己的 PDF 或资料并在资料库找到。
- 用户能为资料打标签并通过标签墙筛选。
- 用户能用目录和关系链组织知识。
- 用户能打开原文 PDF 和译文 PDF。
- 用户能高亮、下划线、批注、删除和撤销标注。
- 用户能写 Markdown 笔记并建立双向链接。
- 用户能把标注、笔记和 AI 对话关联到同一知识对象。
- 插件和 AI Provider 有清晰的扩展入口。
- 所有核心数据重启后仍存在。
- 阅读界面不因为工具栏、侧栏和弹窗占用过多空间。
- 整体体验简洁、稳定，不像静态展示样品。
